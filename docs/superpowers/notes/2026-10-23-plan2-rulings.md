# Plan 2 (power & vitals): rulings

Decisions made while executing Plan 2, each with what it costs if wrong. Overrule any of them in review.

## Rulings

- Ruling P1: the BSP reports `Discovered board version 2 (LCD ST7123, Touch ST7123, FW 3)` on this Tab5 — Tasks 5 and 6 depend on it — costs nothing.
- Ruling P2: `power_log_enable(true)` starts a new run and zeroes the in-RAM summaries (uptime restarts at 0 each boot, so mixing runs would break the energy maths); the NVS `sum` blob from the previous run is loaded at boot only so `power log status` can still show it after a brownout — costs a lost summary if someone toggles the log off and on within one boot.
- Ruling P3: the bench reads its step summaries from the log's per-tag sums (tag 0x10+n) instead of keeping its own; it turns the log on for the run and restores the previous setting — one sampling path, one set of numbers — costs a coupling between bench and log if wrong.
- Ruling P4: `power_bench_tag()` is added to the bench interface so the idle task tags samples with the running step; Task 5 will replace the `0` default with the power state — costs one extra function.
- Ruling P5: `power` prints `state=- idle=- holds=-` (all three) until Task 5, following the brief's text rather than its example's `holds=none` — costs a one-word change.
- Ruling P6: `power_report.py --bench` estimates battery life with an equal-weight mix of the steps that ran ok; a real mix needs the Task 10 usage profile — costs a rough number labelled "(estimate)".
- Ruling P7 (revised in fix round 1): `mw` is computed as mV x |mA| / 1000, rounded, not read from the INA226 power register (25 mW steps, unsigned) — low-power figures decide Plan 2's defaults — costs nothing; the raw register is no longer logged.
- Ruling P8: a sample is "charging" when ma < 0 or the charge pin is low (flag bit2). It stays in the ring but is kept out of the per-tag sums, bench steps and `power_report --log` (unless `--include-charging`); the fast bench runs on USB, so it lets them in — otherwise its scaffold check could never pass — costs a fast run that doesn't prove the exclusion.
- Ruling P9: if USB appears mid-step the bench keeps going and marks that step `usb`; later steps still run — the rest of the run stays useful and the bad step is labelled — costs a long run with several `usb` rows if the cable stays in. A step with n = 0 reports `no samples`; no INA226 refuses the start, and a log that can't enable stops the run with a reason shown by `power bench status`.
- Ruling P10: a step is stored as `running` in NVS when it starts and reports `interrupted` after a reset, with the partial data from the log's NVS `sum` blob if the log hasn't been re-enabled; the blob is only saved every 60 s, so short steps show no data — costs partial data up to 60 s stale.
- Ruling P11: during `power log dump`, samples are not pushed to the ring (sums keep updating) and `clear` is refused — the header count and row indices stay true without copying 768 KB — costs missing samples for the length of a dump.
- Ruling P12: energy uses the sample count as the seconds covered (1 Hz) instead of last_t - first_t + 1, which overstates interleaved tags; the brief's test still gives 1667 — costs nothing at 1 Hz.
- Ruling P13 (Task 2, PT6): power source comes from the pure `vitals_src_step` (`vitals.c`), used by `sysinfo_poll` and so by the bench's battery wait. No VBUS or USB-present signal is known: the BSP header names no VBUS or charge-status pin (only the output enables), and the fork read the charge pin (IO expander pin 4, low = charging) plus the INA226 current and bus voltage. On the device, on USB with Wi-Fi, Tailscale and the dashboard active (20 reads over ~30 s), the pin read low steadily with 1-2 mA and a steady 7.59 V, so the pin looks like a USB-present/charger-active signal, not a current indicator. Rules: pin low or current below -50 mA (leave at -20) is USB-charging at once; battery needs the pin not low and at least 20 mA (leave below 5 mA) for 10 samples in a row (about 10 s at 1 Hz), so short pack bursts under load on USB never read as battery; a bus below 5.5 V is unknown, never battery; above 8.3 V (leave 8.25) with a near-zero current is USB-standby. The old 80 mA threshold read an idle device on battery (30 mA) as USB. `test_usb_with_pack_supplementing` and `test_src_battery_sustained` cover it — costs a 10 s delay before an unplugged device reads as battery, and a wrong guess if the pin does not go low on every charger; the battery side is unverified on hardware until the unplug check in Task 10.
- Ruling P14 (Task 2): the percent now uses the 2S curve on the load-compensated, EMA-smoothed voltage, so the same pack reads 51% where the old linear formula read 61% — the curve is the plan's — costs nothing.
- Ruling P15 (Task 2): the vitals group is created inside the dashboard's bar (`ui_vitals_create(bar)`) and exposes the link dot and host through `ui_vitals_link_dot/host`, so the dashboard keeps its link logic unchanged and the brand label stays in the dashboard — costs two accessors.
- Ruling P16 (Task 2): when migrating from v17 or older, every Plan 2 field is set to its default explicitly, because the old blob's tail padding can overlap the first new bytes — costs nothing.
- Ruling P13 amendment (Task 2 fix round 1, PT8): with the charge pin not low, a bus at 8.25 V or more is USB-standby and never starts or continues a battery run, so a full pack on USB under load cannot read as battery. Battery -> USB at once only on the pin going low or the current below -5 mA; a low current alone (5-20 mA, even 0) on battery stays battery. While a battery run is being counted the previous source is reported (unknown after a boot). Remaining limit: a full pack just unplugged reads USB-standby until it sags below 8.25 V — costs delayed on-battery gates in that window.
- Ruling P17 (Task 3): mode 0 ("bind"): not observed yet — `power light test bind` wrote mode 0 at brightness 60 to the A164 (the console printed `ok`, `kbd: 0 60 00 00 00`) and `test user` restored the owner's choice; nobody has looked at the keyboard, so Task 10 Step 4 has the user look — costs nothing until then.
- Ruling P18 (Task 3): the light age uses `cc_poll_last_ok_ms()`, read when the rule runs, not a time stored by the subscriber callback, and the power task re-evaluates every 10 s — so Task 4's watch results keep the light fresh and a silent link drops the amber after the age limit — costs one 10 s wake of a priority-3 task.
- Ruling P19 (Task 3): `cc_poll_last_ok_ms` takes the cc_link lock (a 64-bit read is not atomic on this 32-bit core); it never blocks for long because the lock only guards short copies — costs nothing.
- Ruling P20 (Task 3): console reason order is `setting off`, then `result too old` (needs-you but stale), then `needs you: <name>`, else `nobody needs you`; `setting off` shows whether or not anything needs you — the brief lists the four words without an order — costs nothing.
- Ruling P21 (Task 3): a session counts for the light only when background and live (has a pid). The user's own sessions that wait for input but have no pid (stopped, shown NEEDS YOU on the dashboard) do not light the keyboard, so the dashboard can say "4 need you" while the light is the user's colour — it is the brief's rule; the dashboard card for such a session is "Stopped" and can't be answered from the device — costs a possible "why no amber?" question; revisit if wanted.
- Ruling P22 (Task 3): extra API beyond the brief: `power_kbd_light_explain` (the choice and its reason, for the console), `power_kbd_light_test` and `keyboard_mark_absent` (debug re-probe). `test bind` holds the owner off until `test user` or `test reprobe`, so the periodic re-check can't undo the probe — costs nothing.
- Ruling P23 (Task 3): there is no hex-entry path for the keyboard colour in the UI or console today, so "refused on entry" is satisfied by the preset list alone (no gold, no orange) plus the load-time reset of an amber-like saved colour to 0x0080FF — add a check if a hex field is ever added.
- Ruling P24 (Task 3): the bench steps `off-light-amber` and `off-light-off` exist now (90 s each) and report "skipped: not built" until Task 5 provides Off — the report shows 4 rows — costs nothing.
- Ruling P25 (Task 3): the colour menu screenshot on the device was not taken: `key ctrl tab` / `key tab` did not move focus to the Settings button on the dashboard in this session, and the dashboard's only other way in is a touch. The preview render of Settings → Input shows the new switch; the preset list is the 6 labels in code — costs one device screenshot for Task 10.
