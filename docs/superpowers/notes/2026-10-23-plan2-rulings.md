# Plan 2 (power & vitals): rulings

Decisions made while executing Plan 2, each with what it costs if wrong. Overrule any of them in review.

## Rulings

- Ruling P1: the BSP reports `Discovered board version 2 (LCD ST7123, Touch ST7123, FW 3)` on this Tab5 — Tasks 5 and 6 depend on it — costs nothing.
- Ruling P2: `power_log_enable(true)` starts a new run and zeroes the in-RAM summaries (uptime restarts at 0 each boot, so mixing runs would break the energy maths); the NVS `sum` blob from the previous run is loaded at boot only so `power log status` can still show it after a brownout — costs a lost summary if someone toggles the log off and on within one boot.
- Ruling P3: the bench reads its step summaries from the log's per-tag sums (tag 0x10+n) instead of keeping its own; it turns the log on for the run and restores the previous setting — one sampling path, one set of numbers — costs a coupling between bench and log if wrong.
- Ruling P4: `power_bench_tag()` is added to the bench interface so the idle task tags samples with the running step; Task 5 will replace the `0` default with the power state — costs one extra function.
- Ruling P5: `power` prints `state=- idle=- holds=-` (all three) until Task 5, following the brief's text rather than its example's `holds=none` — costs a one-word change.
- Ruling P6: `power_report.py --bench` estimates battery life with an equal-weight mix of the steps that ran ok; a real mix needs the Task 10 usage profile — costs a rough number labelled "(estimate)".
- Ruling P7 (revised in fix round 1): `mw` is computed as mV x |mA| / 1000, rounded, not read from the INA226 power register (25 mW steps, unsigned) — low-power figures decide Plan 2's defaults — costs nothing; the raw register is no longer logged.
- Ruling P8: a sample is "charging" when ma < 0 or the charge pin is low (flag bit2). It stays in the ring but is kept out of the per-tag sums, bench steps and `power_report --log` (unless `--include-charging`); the fast bench runs on USB, so it lets them in — otherwise its scaffold check could never pass — costs a fast run that doesn't prove the exclusion.
- Ruling P9: if USB appears mid-step the bench keeps going and marks that step `usb`; later steps still run — the rest of the run stays useful and the bad step is labelled — costs a long run with several `usb` rows if the cable stays in. A step with n = 0 reports `no samples`; no INA226 refuses the start, and a log that can't enable stops the run with a reason shown by `power bench status`.
- Ruling P10: a step is stored as `running` in NVS when it starts and reports `interrupted` after a reset, with the partial data from the log's NVS `sum` blob if the log hasn't been re-enabled; the blob is only saved every 60 s, so short steps show no data — costs partial data up to 60 s stale.
- Ruling P11: during `power log dump`, samples are not pushed to the ring (sums keep updating) and `clear` is refused — the header count and row indices stay true without copying 768 KB — costs missing samples for the length of a dump.
- Ruling P12: energy uses the sample count as the seconds covered (1 Hz) instead of last_t - first_t + 1, which overstates interleaved tags; the brief's test still gives 1667 — costs nothing at 1 Hz.
- Ruling P13 (Task 2, PT6): power source comes from the pure `vitals_src_step` (`vitals.c`), used by `sysinfo_poll` and so by the bench's battery wait. No VBUS or USB-present signal is known: the BSP header names no VBUS or charge-status pin (only the output enables), and the fork read the charge pin (IO expander pin 4, low = charging) plus the INA226 current and bus voltage. On the device, on USB with Wi-Fi, Tailscale and the dashboard active (20 reads over ~30 s), the pin read low steadily with 1-2 mA and a steady 7.59 V, so the pin looks like a USB-present/charger-active signal, not a current indicator. Rules: pin low or current below -50 mA (leave at -20) is USB-charging at once; battery needs the pin not low and at least 20 mA (leave below 5 mA) for 10 samples in a row (about 10 s at 1 Hz), so short pack bursts under load on USB never read as battery; a bus below 5.5 V is unknown, never battery; above 8.3 V (leave 8.25) with a near-zero current is USB-standby. The old 80 mA threshold read an idle device on battery (30 mA) as USB. `test_usb_with_pack_supplementing` and `test_src_battery_sustained` cover it — costs a 10 s delay before an unplugged device reads as battery, and a wrong guess if the pin does not go low on every charger; the battery side is unverified on hardware until the unplug check in Task 10.
- Ruling P14 (Task 2): the percent now uses the 2S curve on the load-compensated, EMA-smoothed voltage, so the same pack reads 51% where the old linear formula read 61% — the curve is the plan's — costs nothing.
- Ruling P15 (Task 2): the vitals group is created inside the dashboard's bar (`ui_vitals_create(bar)`) and exposes the link dot and host through `ui_vitals_link_dot/host`, so the dashboard keeps its link logic unchanged and the brand label stays in the dashboard — costs two accessors.
- Ruling P16 (Task 2): when migrating from v17 or older, every Plan 2 field is set to its default explicitly, because the old blob's tail padding can overlap the first new bytes — costs nothing.
- Ruling P13 amendment (Task 2 fix round 1, PT8): with the charge pin not low, a bus at 8.25 V or more is USB-standby and never starts or continues a battery run, so a full pack on USB under load cannot read as battery. Battery -> USB at once only on the pin going low or the current below -5 mA; a low current alone (5-20 mA, even 0) on battery stays battery. While a battery run is being counted the previous source is reported (unknown after a boot). Remaining limit: a full pack just unplugged reads USB-standby until it sags below 8.25 V — costs delayed on-battery gates in that window.
- Ruling P17 (Task 3): mode 0 ("bind"): not observed yet — `power light test bind` wrote mode 0 at brightness 60 to the A164 (the console printed `ok`, `kbd: 0 60 00 00 00`) and `test user` restored the owner's choice; nobody has looked at the keyboard, so Task 10 Step 4 has the user look — costs nothing until then.
- Ruling P18 (Task 3): the light age uses `cc_poll_last_ok_ms()`, read when the rule runs, not a time stored by the subscriber callback, and the power task re-evaluates every 10 s — so Task 4's watch results keep the light fresh and a silent link drops the amber after the age limit — costs one 10 s wake of a priority-3 task.
- Ruling P19 (Task 3): `cc_poll_last_ok_ms` takes the cc_link lock (a 64-bit read is not atomic on this 32-bit core); it never blocks for long because the lock only guards short copies — costs nothing.
- Ruling P20 (Task 3): console reason order is `setting off`, then `result too old` (needs-you but stale), then `needs you: <name>`, else `nobody needs you`; `setting off` shows whether or not anything needs you — the brief lists the four words without an order — costs nothing.
- Ruling P21 (Task 3): a session counts for the light only when background and live (has a pid). The user's own sessions that wait for input but have no pid (stopped, shown NEEDS YOU on the dashboard) do not light the keyboard, so the dashboard can say "4 need you" while the light is the user's colour — it is the brief's rule; the dashboard card for such a session is "Stopped" and can't be answered from the device — costs a possible "why no amber?" question; revisit if wanted. — REPLACED by controller ruling PT9 (fix round 1): one predicate `cc_session_needs_you` (background, live, CC_NEEDS_YOU) feeds `cc_summary`, the dashboard pill and amber styling, and the keyboard light; a stopped blocked session shows a muted STOPPED pill (interactive: WAITING) and is not counted.
- Ruling P22 (Task 3): extra API beyond the brief: `power_kbd_light_explain` (the choice and its reason, for the console), `power_kbd_light_test` and `keyboard_mark_absent` (debug re-probe). `test bind` holds the owner off until `test user` or `test reprobe`, so the periodic re-check can't undo the probe — costs nothing.
- Ruling P23 (Task 3): there is no hex-entry path for the keyboard colour in the UI or console today, so "refused on entry" is satisfied by the preset list alone (no gold, no orange) plus the load-time reset of an amber-like saved colour to 0x0080FF — add a check if a hex field is ever added.
- Ruling P24 (Task 3): the bench steps `off-light-amber` and `off-light-off` exist now (90 s each) and report "skipped: not built" until Task 5 provides Off — the report shows 4 rows — costs nothing.
- Ruling P25 (Task 3): the colour menu screenshot on the device was not taken: `key ctrl tab` / `key tab` did not move focus to the Settings button on the dashboard in this session, and the dashboard's only other way in is a touch. The preview render of Settings → Input shows the new switch; the preset list is the 6 labels in code — costs one device screenshot for Task 10.
- Ruling P26 (Task 3 fix round 1): LED writes are serialized by a recursive mutex in keyboard.c (`keyboard_led_lock/unlock`, `keyboard_write_led` returns success). kb_probe and the power task's apply_light hold it around choose-and-write, so an older colour can't land after a newer one. Lock order is LED lock, then power lock, then cc_link lock; nothing takes the LED lock while holding the others, and the I2C bus has no lock of ours (the IDF driver locks per transaction) — costs the kbd task waiting a few ms on a write.
- Ruling P27 (Task 3 fix round 1): `s_applied` is recorded only when `keyboard_write_led` succeeded, so an absent keyboard or I2C error retries on the next notify or 10 s tick; the power task force-applies once at start. `led_source` still calls `cc_poll_last_ok_ms()`: cc_link's lock is only ever held for short copies (checked every lock() site, none spans network I/O), so the kbd task can't block long on it — no cache added.
- Ruling P28 (Task 4, deviates from the brief's verbatim loop line): the loop text changed. On the device, the Wi-Fi drop check with the brief's loop left the loop running for 4 min (killed by hand: pid 27830, `I=30`, `sample` showed it blocked in `write()` to its pty). When the Tab5 vanishes mid-block, sshd stops draining the pty, the loop's `printf`/`echo` blocks, and its `read -t` quiet check never runs again. Now a background reader (`{ while :; do j=$SECONDS; if read -r -t "$T" x; ... } <&0 &`) takes the keepalives; on a quiet timeout or EOF (a read that returns before its deadline) it prints `@@CC-BYE quiet|eof` from a background `echo`, waits 0.5 s and runs `kill -- -$$ 2>/dev/null || kill $$; exit` (fix round 1; first `kill 0`). Under sshd's pty session the loop's shell leads its process group, so this takes down the whole group, the blocked writer included. Run outside sshd, where the shell leads no group, the group kill fails with ESRCH and only the loop's shell is killed, never the caller's group; `exit` stops the reader. The main loop sleeps with `sleep "$I"` and ends with `b life`. Markers, change detection, heartbeat, `</dev/null`, `stty -echo` and the `exec /bin/sh -c '…'` wrapper are unchanged. `test_blocked_output_still_exits` (new, RED on the old text) and `test_stdin_eof_exits` cover it, and `test_cmd_watch_exact` pins the new text — why: the global constraint "the long-poll loop leaves nothing running on the Mac" outranks a verbatim string — costs one `sleep` exec every I s on the Mac. Outside sshd (no group of its own) a blocked writer can outlive the shell until the pty closes. `test_not_group_leader_spares_the_caller` (RED with `kill 0`) and `test_blocked_output_plus_stdin_eof` cover it.
- Ruling P29 (Task 4): a heartbeat counts as a fresh result (it stamps `cc_poll_last_ok_ms`, bumps `cc_poll_generation` and calls the subscribers with the current list) only after a good rc-0 block on the same channel. After a failed block it changes nothing, so a failure stays shown and the light can go stale — costs nothing.
- Ruling P30 (Task 4): besides the brief's four status texts there are `watch: starting (link down)` (watch wanted, no link), `watch: off (polling paused)` (effective rate 0) and `no block yet` / `no heartbeat yet` in the `on` line. `companion status` prints the watch line under the link line — costs nothing.
- Ruling P31 (Task 4): with the watch running, the link task waits up to 250 ms on its queue between non-blocking channel reads, so a request waits at most 250 ms and a `cc_link_set_rate`/floor change acts at once (kick). The task wakes 4 times a second; Task 5 may lengthen this with light sleep — costs a 4 Hz wake.
- Ruling P32 (Task 4, replaced in fix round 1 by controller ruling PT11): the dashboard no longer sets rate 30 when its screen is deleted. The rate stays 3 s in Active and Dim on every screen, so the watch runs at I=3 (and, in fallback, the Plan 1 poll also runs every 3 s, the Mac load the watch has anyway). Take-over sets 15, and its close sets 3 again. Task 5's floor sets Off to 15. Every effective-interval change still restarts the channel. `watch_step` and `watch_start` both clamp I to 120, so `s_w_interval`, the liveness limit and the status show the I the loop really runs (review minor 4) — costs a fallback poll every 3 s off the dashboard instead of 30.
- Ruling P33 (Task 4): the banner deadline counts from before the pty request and is checked before each read, so `test-fallback`'s 1 ms is never beaten by a banner already in libssh's buffer (the first device try showed `watch: on` because the check ran after the read) — costs nothing.
- Ruling P34 (Task 4): fallback reasons are `pty request failed`, `exec request failed`, `no banner in 10 s` / `no banner in 1 ms`, `the channel ended 3 times in 5 min` and `bad watch command`. A channel open failure is the link's (`s_drop`, as in Plan 1), not a fallback. A connect and `companion watch on` both clear the fallback and the end count — costs nothing.
- Ruling P35 (Task 4): a paste's or live check's own `refresh()` doesn't clear a watch failure (`s_poll_fails` stays at `CC_POLL_FAILS_SHOWN` until the watch's next good block), because the loop never repeats unchanged output — costs a failure shown a little longer if the Mac recovers without the output changing.
- Ruling P36 (Task 4): `cc_link_park` and the host-key forget don't exist yet. Every Tab5-initiated close goes through `teardown()` or the watch's own close with `asked = true`, so Tasks 5-7 get the not-counted behaviour for free if they close the link that way — costs nothing.
- Ruling P37 (Task 4): the preview's CMakeLists is unchanged. No preview source calls `cc_watch_*`, so only stubs in `preview.c` were needed. The preview builds — costs nothing.
- Ruling P38 (Task 4): the take-over check opened the session with `key ctrl o`, not `key enter`: on a NEEDS YOU card Enter sends the answer box ("Enter sends · Ctrl+O opens the session") — costs nothing.
- Ruling P39 (Task 4): the parser accepts `@@CC-BEGIN` with 1-3 digits, `@@CC-HB` with digits, and `@@CC-BYE` only with `eof`, `quiet` or `life`. Anything else outside a block is ignored as noise — costs nothing.
- Ruling P40 (Task 4, timings on the device with the P28 loop): Mac `ps` count to 0 after a clean close (`companion watch off`): under 1 s (first check). After `wifi leave`: 61 s (limit 3K + I = 63). The last keepalive went out about 1 s before the leave, so this is near the 60 s worst case. After `reboot`: the old loop's pid was gone at the 51 s check (limit 63), and exactly 1 loop ran once the link was back up. With the brief's original loop, the Wi-Fi drop case never reached 0 (P28). Reply to `companion-test-watch2` → not NEEDS_YOU: 2.94 s after `sent` (limit I + 2 = 5). Wi-Fi rejoin → `watch: on` in 8.3 s.
- Ruling P41 (Task 4 fix round 1): `ui settings` was added to the `ui` console command. It opens Settings the way its footer button does, which until now could only be reached by touch (P25). It was used for the PT11 check: on Settings the status stayed `watch: on I=3s` — costs one debug subcommand.
- Ruling P42 (Task 4 fix round 1, device): with the scoped self-kill, the Wi-Fi drop check passed again. The old loop's pid was gone at 61 s (limit 63), with no `@@CC-WATCH` process left. After `wifi join`, `watch: on` returned in 8.1 s with one loop.
- Ruling P43 (Task 5): in Off the touch indev is disabled (`lv_indev_enable(false)`) as well as LVGL being paused. On board v2 the ST7123 driver runs LVGL's touch in event mode, so its INT makes the LVGL task call `lv_indev_read` even with LVGL's timers stopped. Disabling the indev makes the 10 Hz poll the only reader of the controller (the brief's "never races"). — why: otherwise both read it, and a press would reach the LVGL objects while dark — cost if wrong: none found; the indev is re-enabled on wake after the poll stops.
- Ruling P44 (Task 5): "LVGL paused" is `lvgl_port_stop()` (it stops the 5 ms tick), then `lv_timer_enable(true)` and each running timer is paused one by one, and resumed on wake if it still exists. With `lvgl_port_stop()` alone, `lv_timer_handler()` returns 1 ms while timers are disabled, so the LVGL task looped every tick in Off and the CPU never went quiet. Now it sleeps its 500 ms `task_max_sleep_ms`. — why: spec "Quiet tasks in Off" — cost if wrong: a timer created while dark (a console `ui` command) runs with the tick frozen; only period-0 timers fire, so the console still works.
- Ruling P45 (Task 5): cards are marked stale only after a wake from Off or deeper (`power_woke_from() >= PS_OFF`). In Dim the link stays at I = 3 s, and the next block can be 60 s away (the heartbeat), so "Updating…" would sit on fresh cards. The power owner records `cc_poll_generation()` at the wake (`power_wake_gen()`), not the dashboard. A dashboard built later (going home after a needs-you wake, or with Settings open) then judges the same wake the same way. The first version let a dashboard created after a missed wake treat it as new, and it flashed "stale" for 230 ms on a needs-you wake. — cost if wrong: one getter.
- Ruling P46 (Task 5): `power_go(s)` enters s at once and pins it: the ladder leaves it alone until the next wake. `power go active` is a wake (`PW_CONSOLE`). The bench's settle and active steps also set a new `POWER_HOLD_BENCH`, because the ladder would otherwise dim them after 30 s. — why: the bench must measure the state it names — cost if wrong: a console `power go off` doesn't move on to Deep idle until something wakes it.
- Ruling P47 (Task 5): `power_wake_t` gains `PW_RULE` (shown as `rule` in `power wakes`). It means the ladder moved up without input: a hold appeared (a console `reply` while Off holds through `cc_link_busy` and lights the screen), USB without sleep-on-USB, or a longer timeout set while dark. Such a wake bumps the wake sequence like any other. — cost if wrong: one enum value at the end.
- Ruling P48 (Task 5): after each needs-you check, the armed set becomes the current set: new ids join, and ids that stopped needing you leave. A session that is answered on the Mac and blocks again while the screen is off wakes it again. Off entry arms the current set, so a session already waiting never wakes it (checked: `companion-test-ladder`). — cost if wrong: a session that flickers out of NEEDS YOU and back wakes the screen twice.
- Ruling P49 (Task 5): a needs-you wake goes to the dashboard unless the SSH Terminal is on top. Going home would close that SSH session, and the terminal can only be dark when "Stay awake in SSH Terminal" is off. POWER_HOLD_SSH covers the generic SSH Terminal only. A take-over (command mode) has its own POWER_HOLD_TAKEOVER, so `power` shows `holds=takeover`, not `takeover,ssh`. — cost if wrong: one condition.
- Ruling P50 (Task 5): `power set defaults` restores the `pw_*` fields, `kbd_needs_light` and `kbd_off_cap` (`settings_power_defaults()`, split out of Task 2's `plan2_defaults`). It leaves the time zone alone, which is the user's choice and not a power setting. `power settings` adds `ssh-awake` at the end. Settings → Power rows use preset menus (dim 10…600 s, off 20…3600 s, deep idle Off/15…720 min, hibernate Off/1…48 h) through `power_setting_set`, so they get the console's clamps. — cost if wrong: a preset list to extend.
- Ruling P51 (Task 5): while Hibernate isn't built, `hibernate_now()` returns after the 3 s notice and the device goes back to Off. Hibernate is then blocked (`hibernate_ok` false) until the next wake, so the ladder settles on Deep idle or Off instead of re-showing the notice every second. The ladder can't pick Hibernate before Task 6 anyway (`hibernate_supported()` is false); only `power go hibernate` reaches it. — cost if wrong: Task 6 removes the block once Hibernate is real.
- Ruling P52 (Task 5): the IMU hook's host test uses the addendum's name `test_still_brings_hibernate_sooner` with the plan amendment's ten cases. The power task passes `still_ms = 0` and `still_hibernate_ms` = 30 min (addendum) rather than 0 (amendment). Both never fire while `still_ms` is 0. — cost if wrong: none.
- Ruling P53 (Task 5): the USB screenshot (`screenshot` console) now blends `lv_layer_top` (toasts, the mini player, the sleep notice, the transparent shield) over the screen snapshot. Before, the notice and toasts were missing from screenshots, and the brief's Step 5 needs the notice. — cost if wrong: a 3.7 MB PSRAM buffer per screenshot, only while the top layer has children.
- Ruling P54 (Task 5, found on hardware): Settings now builds only its visible category, and switching clears the old panel and fills the new one. LVGL's small objects (≤ 512 B) land in internal RAM, and going home builds the dashboard before Settings is freed. With the new Power panel that peak pushed TLS over the edge: 44 esp-aes "DMA descriptors" failures and an SSH link drop in 4 Settings→home rebuilds, against 0 on the base commit. After the change: 0 in 4, and internal free with Settings open went from 38 KB to 65 KB. The needs-you id sets (516 B each) were also moved to PSRAM. Steady internal free heap is 45.3 KB, the same as the base (45.1–45.3 KB). — cost if wrong: switching category rebuilds its rows (about 50 ms).
- Ruling P55 (Task 5): `idle_poll` waits on a task notification for `power_poll_period_ms()`. It is kicked when the screen wakes and when the power log starts. Without the kick, a bench started from Off lost its first steps' samples to a 10 s sleep that was already running. — cost if wrong: one extra sample per kick.
- Ruling P56 (Task 5): the shield and the state change are made under one display lock (`shield_and_state`). The shield's release handler deletes it while the state is Active, so a release landing between "shield up" and "state Dim/Off" could otherwise leave a dark screen with no shield. — cost if wrong: none.
- Ruling P57 (Task 6, Part A): display teardown and light sleep are dropped, and DFS with them. The spike build (PM + tickless idle) built, and `power spike recreate 10` ran 10 cycles with no crash: internal free 64 003 → 63 979 B (within 4 KB), PSRAM 22 300 760 → 22 300 608 B (within 64 KB), `touch after teardown: ok` every cycle, the dashboard on screen afterwards, the link and watch on 10 min later, no new panic or brownout. It failed on wake-to-picture: 680–688 ms against the 500 ms limit. The ST7123 driver alone takes about 430 ms (SWRESET + 120 ms, 27 init commands × 5 ms, sleep-out 120 ms, display-on 50 ms; `esp_lcd_st7123.c`, `disp_init_data_1.h`), and the LVGL re-create, dashboard build and first refresh take the other 240 ms. The DPI panel's CPU_FREQ_MAX lock has no release short of deleting the panel, so Deep idle keeps the display (panel off) at 360 MHz. Also found: with no display the LVGL port task never runs `lv_timer_handler` and wakes every tick, so a teardown needs a 1×1 placeholder display (the spike's way). The spike's code is kept as a patch in the notes, not in the tree — why: the brief's limit is explicit — cost if wrong: Deep idle pays the P4 at 360 MHz instead of 40 MHz; revisit if a 0.7 s wake after an hour's idle is acceptable.
- Ruling P58 (Task 6, PT15): nothing in the BSP or the fork starts the BMI270 (no `bmi270_create`, no `bsp_sensor_init` call), yet the first read found PWR_CTRL 0x0e (accel, gyro and temperature on) and PWR_CONF 0x00: an earlier firmware left it running, and it keeps power across P4 resets. `app_main` now calls `imu_suspend()` at every boot, besides Hibernate and `floor` — why: the IMU is unused (PT15) and the gyro alone draws on the order of 1 mA — cost if wrong: none; one I²C write per boot.
- Ruling P59 (Task 6, Step 4c): the rail map follows the Tab5 schematic (U6 0x43, U7 0x44). The BSP's LCD_EN, TOUCH_EN and CAMERA_EN are LCD_RST, TP_RST and CAM_RST: resets, not supplies, so "cut" holds them in reset. EXT5V_EN (0x43 P2), USB5V_EN, WLAN_PWR_EN and SPK_EN are real switches and are cut. 0x44 P4 is PWROFF_PULSE (driven only to power off), P6 CHG_STAT, P7 CHG_EN, P5 nCHG_QC_EN: never touched. `sysinfo_charge_pin` now reads P6 (CHG_STAT) instead of P4: P4 is PWROFF_PULSE with the expander's pull-down and reads 0 whatever the supply, so the fork's battery detection could never see a battery. On USB P6 also reads 0, so nothing changes on USB — why: the schematic, and P4 can't be right — cost if wrong: P6's polarity on battery is unverified (Task 10 unplug check); at worst it is as blind as P4 was.
- Ruling P60 (Task 6, Steps 5, 7, 12): `hibernate_mode()` is power-off (PWROFF_PULSE, three 100 ms pulses as the factory firmware does), with sources timer and button. On USB the power-off took: the board went dark with USB in (`E BOD: Brownout detector was triggered`, the port gone). The RX8130 countdown timer, armed for 60 s, did not switch it back on within 120 s, so RTC is not a source; the side button (S1 → SW_PWR on the PMS150G power controller) is the Tab5's documented power-on and is counted on paper until Task 10's press. Any hibernate with a timed wake (`power hib test-wake`, the bench probes, Task 8's check-in) deep-sleeps instead, because only the timer is proved and it works only in deep sleep. `hibernate_h` stays 2 — why: the button is the device's normal power-on, and a USB plug-in edge reaches the same trigger on the schematic — cost if wrong: a Tab5 idle on battery for 2 h stays off until someone plugs USB in.
- Ruling P61 (Task 6, PT16): `hibernate_kbd_rail_survives()` is true, for deep sleep only. The keyboard sits on J9 (SYS_VIN, SYS_EXT5VO, SOC_3.3V); EXT5V_EN driven low didn't drop it (it re-probed), so it has no switchable rail and its share of the floor is not separable. After `power hib test light 60` the A164 still held mode 1, brightness 30, amber (`kbd: light at boot: mode=1 bright=30 rgb=f4b545`), so it stayed powered and unreset through deep sleep. A power-off drops the P4's own supply and so the keyboard. The `hibernate-light` bench step is built — why: the registers show the MCU kept running; the light itself is for the user to see in Task 10 — cost if wrong: Task 8's check-in leaves amber that isn't lit.
- Ruling P62 (Task 6): on this P4 (rev < 3) a deep-sleep timer wake reaches the app as an HP watchdog reset (hw reason 7, `ESP_RST_WDT`) with no wakeup cause, about 0.5 s after the timer. `hib_rules.c` (pure, host-tested) calls it a timer wake when a watchdog or deep-sleep reset lands within −2…+20 s of the armed timer by the RTC-kept clock; `power resets` counts it as `deepsleep`. An RX8130 flag wins over everything, and power-on means the button (or a USB plug-in) — why: the cause register is lost, the clock isn't — cost if wrong: an unrelated watchdog reset just after a timed hibernate reads as a timer wake.
- Ruling P63 (Task 6): `hibernate_now()` pulses PWROFF before cutting any rail: with WLAN_PWR_EN cut first, esp_hosted's next SDIO write failed within 600 ms and it aborted to restart the host. The cuts and the deep sleep follow only if the board is still on. The ladder's hibernate runs on a 6 KB task of its own and the bench task grew to 6 KB: NVS writes, expander I²C and `esp_deep_sleep_start` were never sized for the power task's 4 KB with 2 KB free — why: an abort on the way down and stack headroom — cost if wrong: 6 KB of internal RAM while hibernating or benching.
- Ruling P64 (Task 6): there is still no `cc_link_park` (P36). - Ruling P67 (Task 6 fix round 1, review M5): `imu_suspend()` first turns off the INT1 and INT2 outputs (INT1_IO_CTRL 0x53 and INT2_IO_CTRL 0x54 = 0), sets INT_LATCH to 0, clears the feature and data maps (0x56, 0x57, 0x58) and reads INT_STATUS clear, then sets PWR_CTRL and PWR_CONF. Why: INT1 drives Q8 onto E_TRG, the power controller's trigger. An earlier firmware is known to have left the IMU running, and a stray or latched INT1 level could switch a powered-off board on, or hold the trigger low so that neither the PWROFF pulses nor the button reach it. Cost if wrong: six more I²C writes per suspend.
- Ruling P68 (Task 6 fix round 1, review I1 and I2; amends P60 and P62):
  - I1: a power-off that doesn't take now deep-sleeps with a timer. It keeps the hibernate's own timer when one is set; for an untimed (ladder) hibernate it uses a 60 min backstop, logs `hib: power-off did not take, deep sleep with 60 min backstop`, and records `fell_back` (shown by `power boot`). In deep sleep the side button reaches the power controller of a board that is still on, so nothing proved would wake it. When it wakes, the ladder decides again.
  - I2: an RX8130 flag counts as the wake only when the time asleep matches the armed timer, within the same −2…+20 s window, never under 3 s (M1). A flag outside that window is stale: a timer that fired without switching the board on. That boot counts as the button and logs `the RX8130 fired earlier without switching the board on`. After a power-off, the time asleep comes from the RX8130's own clock (`sysinfo_rtc_epoch_raw`), because the system clock restarts at 0.
  - Why: a dark device with no proven way back, and a mislabelled first proof of the button wake. Cost if wrong: a failed power-off wakes once an hour on battery.
